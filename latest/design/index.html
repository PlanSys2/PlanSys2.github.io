PlanSys2 design

PlanSys2 is made of four ROS 2 lifecycle nodes:

  • Domain Expert (domain_expert): the PDDL domain: types, constants, predicates, functions, derived predicates, actions, processes and events.

  • Problem Expert (problem_expert): the knowledge of the world: instances, predicates, functions with their values, goal, metric and constraints. It also simulates the PDDL+ dynamics and applies the timed facts.

  • Planner (planner): computes plans with plan solver plugins (Kairos by default).

  • Executor (executor): executes a plan as a behavior tree, asking the action performers (the nodes that implement each action) to do each action.

Every name on this page is relative: a namespace given to PlanSys2 applies to all of them. Applications use them through the client libraries (C++ and Python), which hide the services and actions.

Problem Expert

It keeps the knowledge of the world: instances, grounded predicates, functions with their values (numbers or objects), goal, metric and constraints. Every change is published.

While active, every 50 ms it applies the timed initial literals and fluents that are due, and simulates the PDDL+ dynamics: the active processes and the continuous effects of running actions change the functions for the time passed, and then the events whose conditions hold happen.

Planner

It computes plans for a domain and a problem with its plan solver plugins, in parallel, and returns the plans found in time, shortest first. Each plan carries the time it was requested (Plan.stamp), which the executor uses to anchor timed plans.

A task goes only to the plugins that support the PDDL requirements it uses; if none does, the answer says what is missing. See Plugins and Configuring Multiple Planners.

Action

execute_plan (plansys2_msgs/action/ExecutePlan): the goal is a plan; the feedback and the result have the state of each action (ActionExecutionInfo); the result says SUCCESS, FAILURE or PREEMPT.

  • Goals are rejected unless the executor is active.

  • An empty plan succeeds at once.

  • A goal sent while a plan runs replaces it: the previous goal ends with PREEMPT and the plan is repaired (see below).

  • A change of the domain aborts the plan.

Behavior tree builders

Once a plan is obtained, the executor turns it into a behavior tree. Each action becomes a subtree that waits for what the action needs, asks a performer for it, applies its effects and checks its requirements while it runs:

The builder decides what each action waits for. It builds a graph of the dependencies of the plan, pairing what an action needs with the action that provides it before in the plan:

STNBTBuilder (the default) works with the start and the end of each action separately, so an action can start when what it needs happened, also if it is the start of another action. SimpleBTBuilder waits for whole actions; SequentialBTBuilder runs them in the order of the plan.

Timed execution

A plan with timed initial literals or fluents, processes, events, continuous effects or constraints with times runs timed (also any plan, with timed_execution): each action starts at its time in the plan, not before, and a durative action lasts its planned duration.

  • The plan counts from when its problem was read (Plan.stamp), so timed facts and plan share the clock.

  • An action that starts late shifts the rest of the plan with it: the planned intervals hold.

Repairing a plan

A new goal for execute_plan while a plan runs does not start from scratch. The executor:

  1. Builds the behavior tree of the new plan.

  2. Keeps the running actions that the new plan starts with (same action at time 0): they go on without interruption, their continuous effects included, and their performer is told their new duration (ActionExecution.UPDATE).

  3. Stops the others, undoes their at start effects and stops their continuous effects.

  4. Keeps the history of the constraint monitor.

To replan while a plan runs, ask the problem to plan from to the executor (executor/get_replanning_problem, ExecutorClient::get_replanning_problem()): it is the current problem with the at start effects of the running actions undone, so a plan from it can keep them. The trace says which actions went on and which were dropped (REPLAN).

Several planners give alternative plans for the same task (PlannerClient::getPlanArray()); an application decides when to replace the running plan. These mechanisms are described in Peña-Narváez et al., “LLM-Assisted Plan Execution for Robots in Dynamic Environments” (Robotics, 2026), with a reference implementation in paper_plansys2_LLMs.

Constraints

The hard trajectory constraints of the problem (always, sometime, within, at-most-once, sometime-before…) are checked while the plan runs: when the knowledge changes, and at their deadlines. A violation fails the plan and says which constraint (VIOLATION in the trace). Preferences are only for the planner.

Action performers

An action performer is the node that does an action of the plan. It inherits from plansys2::ActionExecutorClient (C++) or plansys2_support_py.ActionExecutorClient (Python) and implements do_work(), which is called periodically while it runs the action. Several performers can do the same action (one per robot, for instance): the executor gives each action to one of them.

Protocol

The executor and the performers talk on actions_hub (plansys2_msgs/msg/ActionExecution). Each request has its own id, carried by every message about it.

  1. REQUEST (executor): who can do this action, with these arguments? It carries the planned duration.

  2. RESPONSE (performers): the free performers that can do it answer, and wait up to 5 s for an answer.

  3. CONFIRM (executor) to the first one, which activates and starts calling do_work(); REJECT to the others, which are free again. A free performer is asked again at once; with no answer, the request is repeated every second.

  4. FEEDBACK (performer): progress and status, from send_feedback().

  5. FINISH (performer): success or failure, from finish().

  6. CANCEL (executor): stop the action, for instance when the plan is cancelled.

  7. UPDATE (executor): a repaired plan gives the running action another duration (get_planned_duration() returns it).

Each side watches the other: the executor fails the action if its performer disappears, and a performer stops if the node that asked for the action disappears.

API

In C++ (plansys2_executor/ActionExecutorClient.hpp):

// Constructor: the node name
ActionExecutorClient(const std::string & node_name);

virtual void do_work();                 // To implement: called at `rate` while running
const std::vector<std::string> & get_arguments();  // The arguments of the action

In Python (plansys2_support_py.ActionExecutorClient), the constructor is ActionExecutorClient(node_name, period) (period in seconds; the rate parameter, in Hz, overrides it) and the methods are do_work(), get_planned_duration(), send_feedback(completion, status) and finish(success, completion, status).

Client libraries

Applications use PlanSys2 through clients that hide the services and actions. A client creates no node: it works on the node of the application, given to its constructor, and its names are relative to the namespace of that node. Inside PlanSys2, each component has a single node too, and its clients work on it: PlanSys2 has four nodes, domain_expert, problem_expert, planner and executor.

// In a node of the application (rclcpp::Node or rclcpp_lifecycle::LifecycleNode)
domain_expert_ = std::make_shared<plansys2::DomainExpertClient>(*this);
// Or with the shared pointer of a node
auto problem_expert = std::make_shared<plansys2::ProblemExpertClient>(node);

A client brings its own answers: its service and action clients and its subscriptions go in a callback group of its own, which the executor of the node does not take, and the client serves that group, and only it, while it waits for an answer; feedback, results and the problem published meanwhile come at the next call. So the application spins its node as it likes, or not at all: a call works from main before any spin, and from a callback of any executor, single threaded too. The client does not own the node: it must not outlive it.

auto node = std::make_shared<MyController>();  // its clients take *this
node->run();  // calls the clients: nothing to spin

// Or with callbacks of its own: step() in a timer, the calls in it
rclcpp::spin(node);

As any blocking call, a call from a callback keeps its thread while it waits; the migration guide shows how a controller with subscriptions of its own spins its node. Inside PlanSys2, only plansys2_node (and, in the distributed bringup, the main of each node) spins, with a MultiThreadedExecutor per node.

Every call of a client waits until its component is active, however long it takes while ROS runs, and goes on as soon as it is: an application may start before PlanSys2, or while it starts, and needs no wait of its own. While it waits, the client says so every few seconds. Once seen active, the component is not asked again, until one of its services goes or stops answering: then the next call waits for it again, so the application also goes on after PlanSys2 restarts. wait_active() is the same wait alone, for code that must not start before (the greenhouse example, whose world evolves from the moment its problem is loaded). Call the clients from a thread of their own if the application must not block.

A request without answer is sent again, up to three times, each with a new client: some middlewares lose every answer to a client whose connection was set up badly while many processes started at once, and waiting longer on the same client does not help. Only requests that can be repeated are sent again: queries, and changes that leave the same state when repeated.

C++

plansys2::DomainExpertClient (plansys2_domain_expert/DomainExpertClient.hpp): getName, getTypes, getConstants, getPredicates, getPredicate, getFunctions, getFunction, getDerivedPredicates, getDerivedPredicate, getDerivedResolutionGraph, getActions, getAction, getDurativeActions, getDurativeAction, getProcesses, getProcess, getEvents, getEvent, getDomain, changeDomain.

plansys2::ProblemExpertClient (plansys2_problem_expert/ProblemExpertClient.hpp):

  • instances: getInstances, tryGetInstances, addInstance, removeInstance, getInstance;

  • predicates: getPredicates, tryGetPredicates, addPredicate, removePredicate, existPredicate, tryExistPredicate, getPredicate;

  • functions: getFunctions, addFunction, removeFunction, existFunction, tryExistFunction, updateFunction, getFunction;

  • goal and metric: getGoal, setGoal, isGoalSatisfied, clearGoal, getMetric, setMetric, clearMetric;

  • the whole problem: clearKnowledge, getProblem, getProblemWithTimestamp, addProblem, getUpdateTime.

The try* methods tell “nothing” from “no answer”.

plansys2::PlannerClient (plansys2_planner/PlannerClient.hpp): getPlan(domain, problem) returns the best plan, getPlanArray(domain, problem) all of them. It waits for the answer as long as the planner plans (the planner’s plan_solver_timeout) and a margin of 5 s; its own plan_solver_timeout parameter, if positive, sets that time instead.

plansys2::ExecutorClient (plansys2_executor/ExecutorClient.hpp):

  • start_plan_execution(plan): sends the plan (replaces the running one, if any).

  • execute_and_check_plan(): call it periodically; false when the plan ended.

  • getFeedBack(), getResult(): the state of the actions; the result once ended.

  • cancel_plan_execution().

  • get_plan(), get_remaining_plan(), getOrderedSubGoals(), get_replanning_problem().

Python

plansys2_support_py has the same clients: DomainExpertClient, ProblemExpertClient, PlannerClient and ExecutorClient, with snake case methods named after the services (get_domain_types(), add_problem_instance(), get_plan(), start_plan_execution()…), plus validate_domain() in PlannerClient and get_replanning_problem() in ExecutorClient.

They also take the node of the application (DomainExpertClient(node)) and bring their own answers. rclpy executors take whole nodes, not callback groups, so each Python client has a node of its own, <node>_<component>_client in the namespace of the node of the application, which it serves while it waits.

Running PlanSys2

plansys2_bringup starts the four nodes and brings them to active:

  • Monolithic (plansys2_bringup_launch_monolithic.py): one process, plansys2_node, with the four nodes, each on its own thread.

  • Distributed (plansys2_bringup_launch_distributed.py): one process per node, and the lifecycle_manager node that configures and activates them, and then keeps watching them.

Both take these launch arguments:

Argument

Meaning

model_file

The PDDL domain (required); several files separated by :.

problem_file

A PDDL problem to load at start (optional).

namespace

Namespace of every node, topic and service.

params_file

Parameters of the nodes; by default plansys2_bringup/params/plansys2_params.yaml.

bt_builder_plugin

The BT builder of the executor (STNBTBuilder by default).

action_bt_file, start_action_bt_file, end_action_bt_file

Behavior tree templates of the executor.

respawn

Start a process again, 1 s later, if it ends (true by default).

state_file

Where the problem expert keeps its problem; by default a file of this launch in the temporary folder, so a new launch does not take the problem of another. Empty: not kept.

The nodes are configured in the order planner, domain expert, problem expert, executor, and activated in the order domain expert, problem expert, planner, executor; each transition waits up to startup_timeout seconds (default 5). plansys2_node can run with real-time priority, and stops if the system does not allow it. In the monolithic bringup, both are launch arguments (use_real_time:=true, startup_timeout:=10), passed to plansys2_node as --use-real-time true and --startup-timeout 10: it has no node of its own to read them from. In the distributed one, startup_timeout is a parameter of lifecycle_manager.

When something dies, the bringups bring it back. A process that ends starts again (respawn), and the problem expert comes back with the problem it had (state_file). In the distributed bringup, lifecycle_manager keeps watching the four nodes once they are active: it brings up a node that starts again, and if one is gone for longer than a grace time, it deactivates the executor, so that the plan fails, until the node is back. Messages

The main messages of plansys2_msgs:

  • Plan: items (PlanItem: time, action, duration), stamp (when its problem was read), has_end/end (end of a PDDL+ plan), has_cost/cost.

  • Knowledge: instances, predicates, functions (with their values, e.g. (= (battery r1) 10.5)), goal, metric, constraints.

  • ActionExecution: the performer protocol (REQUEST, RESPONSE, CONFIRM, REJECT, FEEDBACK, FINISH, CANCEL, UPDATE), with node_id, request_id, action, arguments, success, completion, status and planned_duration.

  • ActionExecutionInfo: the state of an action of the plan (NOT_EXECUTED, EXECUTING, FAILED, SUCCEEDED, CANCELLED), its full name, times, duration, completion and message.

  • ExecutionEvent: an event of the execution trace (see Reading an execution).

  • ActionPerformerStatus: the state of a performer.
